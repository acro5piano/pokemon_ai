SECTION 01このプロジェクトは何をしたのか

やったことを一言で言うと、「ポケモンバトルのルールを自分で書いて、そこで戦うAIを、人間の対戦データをいっさい使わずに、AI同士の対戦だけで育てた」です。

ポイントは 全部スクラッチ（ゼロから手書き） だということ。バトルエンジンも、学習アルゴリズムも、経験を貯めるメモリも自分で書いています。使っている外部ライブラリは numpy と、ニューラルネットの部分に scikit-learn の MLPRegressor だけ。PyTorch も Gymnasium も、RL フレームワークは一切使っていません。

1,518行（テスト込み）
54個のテスト（pytest）
4,000エピソード ≒ 12分で学習完了
0件の人間の対戦データ

なぜ「自己対戦（self-play）」なのか

囲碁の AlphaGo Zero が有名にしたやり方です。強い教師データが無くても、AIが自分のコピーと何万回も対戦して、勝った手を強化し、負けた手を弱めることを繰り返すと、勝手に強くなっていきます。相手も同時に強くなるので、自動的に「ちょうどいい難易度の練習相手」が無限に湧いてくる、というのが美味しいところです。

SECTION 02舞台：3匹だけの「三すくみ」バトル

本物のポケモンは複雑すぎるので、思い切って削ります。ルールはこれだけ：

  • 初代（赤・緑）の計算式、レベル100、個体値・努力値マックス
  • 技は必ず当たる（命中率なし）・急所なし・変化技なし・追加効果なし・PP無限
  • 両プレイヤーともまったく同じ3匹を使う。だから決めるのは「誰を先頭に出すか」「いつ誰に交代するか」「どっちの技を使うか」だけ
  • ダメージの乱数（217〜255の揺れ）だけは残したので、同じ手でも結果はブレる

この3匹はジャンケンになっている

これがこのプロジェクトのいちばん面白いところです。3匹の相性がきれいな三すくみ（ジャンケン）になるように選ばれています。

これが効いてくる理由
ジャンケンには「これを出しておけば必ず勝てる手」がありません（＝純粋戦略の均衡が存在しない）。だから自己対戦AIは「グーを覚える→パーを覚える→チョキを覚える→またグー…」と永遠にぐるぐる回ります。あとで出てくる勝率のガタガタは、AIのバグではなくこのゲームの性質そのものです。

SECTION 03バトルエンジン ― ルールをコードにする

pokemon_rl/battle.py（258行）が審判役です。バトルは 3つのフェーズ を行き来する状態マシンとして書かれています。

1ターンの解決順（ここ大事）

本物のポケモンと同じで、両者は相手の手を見ずに同時に選びます。そのうえで：

① 交代をする人が先に交代する（だから交代には「相手の技を1発もらう」リスクがある）
② 残った攻撃を、すばやさの高い順に処理する（同速ならコイントス）
③ 技を出す前に自分が倒れていたら、その攻撃は不発

pokemon_rl/battle.py
def _resolve_turn(self, actions: dict[int, int]) -> None:
    self.turn += 1

    # ① 交代が先に解決される
    for side in SIDES:
        if actions[side] >= MOVE_ACTIONS:
            slot = actions[side] - MOVE_ACTIONS
            self.active[side] = slot

    # ② 残りの攻撃をすばやさ順に
    attackers = [side for side in SIDES if actions[side] < MOVE_ACTIONS]
    for side in self._move_order(attackers):
        if self.require_active(side).fainted:
            continue                      # ③ もう倒れていたら不発
        self._use_move(side, actions[side])

ダメージ計算

初代の計算式そのままです。急所と命中判定だけ抜いてあります。

pokemon_rl/battle.py
damage = ((2 * LEVEL // 5 + 2) * move.power * attack // defense) // 50 + 2
if move.type in attacker.species.types:
    damage = damage * 3 // 2       # タイプ一致ボーナス（STAB）
damage = int(damage * effectiveness)   # 0倍 / 0.5倍 / 2倍 / 4倍
damage = damage * roll // 255          # roll は 217〜255 の乱数

// は整数の割り算です。初代は全部整数で計算していたので、そこも再現しています。最後の roll のおかげで、まったく同じ状況でも約15%ダメージがブレます。これがあるから「たまたま勝った」を学習しないで済む、というのが地味に重要です。

6匹 × 3項目（HP割合 / 生きてるか / 場に出てるか）＋ フェーズフラグ1個 ＝ 19

重要なのは 「自分のチームが必ず先に来る」 こと。そのおかげで、P1として学んだことがそのままP2としても使えます。1つのネットワークで両サイドを指せるのはこの設計のおかげです（observation(side) が for owner in (side, 1 - side) と書かれている理由）。

手：5つの行動と「合法手マスク」

この「マスク」がこのプロジェクトの隠れた重要ポイントです。行動を選ぶときだけでなく、学習の目標値を計算するときにもマスクを掛けます。 掛け忘れると「もうひんししている子に交代する」というあり得ない手の価値を根拠に学習してしまい、Q値が壊れます。

pokemon_rl/agents.py
def _masked_argmax(values: np.ndarray, mask: np.ndarray) -> int:
    masked = np.where(mask, values, -np.inf)   # 非合法手を -∞ にする
    return int(np.argmax(masked))

SECTION 05DQNのキモ ― 「Q値」って何？

Q値とは、ひとことで言えば 「この場面でこの手を打ったら、最終的にどれくらい得するかの見積もり」 です。

学習の式：Q値を「正解」に近づける

正解ラベルなんてどこにも無いのに、どうやって学習するのか。答えは 「1手先の自分の予想」を正解の代わりに使う、です。これをベルマン方程式と言います。

Q(今の盤面, 打った手) を
もらった報酬 + 0.98 × max Q(次の盤面, 合法手すべて) に近づける

「いま報酬をもらってないけど、次の場面がすごく良さそうなら、いまの手も良かったはず」という理屈でスコアが過去にじわじわ伝わっていきます。0.98（＝gamma）は「先の未来ほど少し割り引く」係数です。

pokemon_rl/agents.py — 1回の更新のすべて
batch = self.buffer.sample(self.batch_size)          # 経験を64件ランダムに取り出す

next_q = self.target_model.predict(next_states)      # ターゲットネットで次の盤面を評価
next_q = np.where(next_masks, next_q, -np.inf)       # 非合法手を潰す
best_next = np.where(next_masks.any(axis=1), next_q.max(axis=1), 0.0)

targets_for_action = rewards + np.where(dones, 0.0, self.gamma * best_next)

targets = self.model.predict(states)                 # いまの予想を全部そのまま持ってきて
targets[rows, actions] = targets_for_action          # 実際に打った手の分だけ差し替える
self.model.partial_fit(states, targets)              # 1回だけ勾配を流す

「打った手の分だけ差し替える」のがミソです。5つの出力のうち、実際に試した1つしか答え合わせできません。残り4つは自分の予想をそのまま目標にするので、勾配がゼロになり、変化しません。

DQNが安定するための3つの仕掛け

① リプレイバッファ

直近の経験を 5万件 貯めておき、そこからランダムに64件取り出して学習。連続した経験だけで学ぶと「似た場面ばかり」で偏るのを防ぐ。

② ターゲットネットワーク

正解を作る用のネットは1,000回に1回だけコピーして固定する。目標が動き続けると、自分の影を追いかけて発散してしまうため。

③ ε（イプシロン）グリーディ

確率εでわざとランダムな手を打つ。最初は100%ランダム、3万ステップかけて5%まで下げる。知らない手を試さないと、良い手に気づけない。

（おまけ）ネットは scikit-learn

MLPRegressor の partial_fit を1回呼ぶ＝1回の勾配ステップ、と読み替えて使っている。PyTorch なしでDQNが書ける。

SECTION 06報酬のつけ方 ― 勝ち負け＋HP差

いちばん素直な報酬は「勝ったら +1、負けたら −1、引き分け 0」です。でもこれだけだと、1戦40ターン近く指した末にようやく1回だけ点がもらえることになり、「どの手が良かったのか」がさっぱり伝わりません（報酬がスパースな問題）。

そこで 報酬シェイピング を足しています：

報酬 ＝ 勝敗（±1） ＋ 0.5 × HP差の変化量

HP差 =（自分の残りHP合計 − 相手の残りHP合計）÷ 3匹 → −1 〜 +1

これで「相手に大ダメージを与えた手」はその場ですぐ小さなプラスをもらえます。4倍のなみのりでサイドンを一撃で落とすと、HP差が一気に動くので、そのときの行動のQ値がぐっと上がるわけです。

「行動と行動のあいだ」をどう繋ぐか

ここは実装上の地味な落とし穴でした。ポケモンバトルは片側だけが行動する瞬間があります（相手だけがひんしで交代する場面）。つまり、自分の「次の判断」は1ステップ後とは限りません。

コードでは各サイドの「まだ閉じていない判断」を pending に持っておき、次の判断が来たときに初めて経験として確定させます。

pokemon_rl/selfplay.py
def push(side, next_state, next_mask, done, terminal_reward=0.0):
    state, action, hp_diff_before = pending[side]
    # 「前回判断したとき」からのHP差の動きが、まるごと報酬になる
    reward = shaping * (battle.hp_diff(side) - hp_diff_before) + terminal_reward
    learner.remember(Transition(state, action, reward, next_state, next_mask, done))
    pending[side] = None

SECTION 07自己対戦ループ ― 1エピソードの流れ

ここまでの部品が全部つながります。「1エピソード＝1バトル」で、以下がひたすら4,000回繰り返されます。

pokemon_rl/selfplay.py — ループの本体
while not battle.done:
    actions, acting = {}, []
    for side in SIDES:
        if battle.needs_action(side):                  # 行動が必要なサイドだけ
            state = battle.observation(side)
            mask  = battle.legal_mask(side)
            action = policies[side].act(state, mask, greedy=greedy)
            actions[side] = action
            acting.append((side, state, mask, action))

    for side, state, mask, action in acting:
        if learner is not None and side in learner_sides and pending[side] is not None:
            push(side, state, mask, done=False)         # 前回の判断をここで確定
        pending[side] = (state, action, battle.hp_diff(side))

    battle.step(actions)

SECTION 08「リーグ」で過去の自分とも戦う

純粋な自己対戦には弱点があります。相手が常に「いまの自分」だと、ジャンケンをぐるぐる回るだけになるのです。「グーばっかり出す自分」に勝つためパーを覚える → じゃあパー対策にチョキ → チョキ対策にグー…と、前に倒したはずの戦法にまた負けるようになる（catastrophic forgetting）。

対策が リーグ（opponent pool） です。

pokemon_rl/train.py
if args.snapshot_every and episode % args.snapshot_every == 0:
    snapshot = agent.snapshot(epsilon=args.epsilon_end, seed=args.seed + episode)
    if len(pool) < args.pool_size:
        pool.append(snapshot)
    else:
        # 古い順ではなく「ランダムな1体」を置き換える。
        # こうしないとリーグが学習者と一緒に漂流してしまい、
        # 三すくみをぐるぐる回る問題が解決しない。
        pool[rng.randrange(len(pool))] = snapshot

ランダム置換がポイント
普通のキューだと「直近20体」しか残らず、リーグ全体が学習者と一緒に漂流します。ランダムに潰すと 古いスナップショットほど長生きするので、初期の素朴な戦法もずっと練習相手として残る。この一行の変更で、後述の greedy 相手の勝率が 約56% → 約75% に上がりました。

評価用の2つの「台本AI」

強さを測るためだけに、学習しない相手も用意してあります（学習には一切使いません）。

相手中身
RandomAgent合法手から完全ランダム。最低ラインのチェック用
GreedyAgent常に「いちばんダメージの出る技」を撃ち、自分からは交代しない。ひんし時だけ「与ダメ − 被ダメ」が最大の子を出す。人間の初心者の動きに近く、これがなかなか強い

SECTION 09学習結果 ― グラフと、暴れる勝率のわけ

デフォルト設定（4,000エピソード、ノートPCのCPUで約12分）での実測値がこちらです。

95〜100%vs ランダム（終始安定）
約75%vs グリーディ（後半の平均）
100%ベスト版 vs グリーディ（200/200）
17万勾配ステップ / 12分

オレンジ線がガタガタなのはバグ？ → いいえ、ゲームのせい

ep 1250 で 87.5% → ep 1500 で 47% → ep 1750 で 92% → ep 2500 で 33%…と、勝率が平気で40ポイント跳ねます。最適化がおかしいのではなく、3匹が三すくみだから「どんな固定相手にも強い唯一の戦法」が存在しないためです。

自己対戦AIは三すくみの上をぐるぐる回り続けます。そして グリーディは「固定の1手」 なので、AIがサイクルのどこにいるかによって、たまたま相性が良かったり悪かったりする。vs ランダムがずっと安定しているのは、ランダムには特定の戦法が無いからです — この対比が「振動の原因は三すくみ」という証拠になっています。

対処

  • リーグを広げる（--pool-size、--snapshot-every、--pool-prob）と振動は弱まる
  • そもそも完全には消せないので、評価ごとにいちばん強かった瞬間のチェックポイントを runs/dqn-best.pkl に保存しておく

ちゃんと「わかって」いるのかの確認

学習済みポリシーの挙動を見ると、知識が入っているのがわかります。

  • 先発はスターミーを選ぶ（最速・4倍技持ち）
  • 相手がサイドンなら1ターン目になみのりで確定1発（4倍＝確1）
  • 逆に、弱いチェックポイントは相手のサンダーに自分のサンダーを当てにいく（正解はサイドン。10まんボルトが無効になる）── これが「まだ分かってない」サイン

まとめ：このプロジェクトの学びどころ

  • DQNは意外と短く書ける。 本体は train_step() の20行ちょっと
  • 合法手マスクは、行動選択だけでなく目標計算にも要る。 忘れると静かに壊れる
  • 報酬シェイピングは「長い試合」の必需品。 HP差を足すだけで学習速度が段違い
  • 自己対戦だけだと過去を忘れる。 リーグを持ち、しかもランダム置換にするのが効く
  • 勝率が振動したら、まずゲームの性質を疑う。 三すくみには「最強の固定戦法」が無い

ブランチ pokemon-dqn ／ 実装はすべてスクラッチ（RLフレームワーク不使用）
